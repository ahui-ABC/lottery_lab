## 1. 用「赔率变化」改进预测 【优先级：中，需先攒数据】

### 现状

赔率变化**已经被采集，但完全没有参与任何计算**。

```
collect-odds --watch  →  odds_snapshots 表（只写不读）
                      ↘  period_matches.odds_json 的 "jc" 键（只保留最新值）
                                    ↓
                              devig() → 市场概率 → 求解方案
```

- `odds_snapshots` 全库唯一的读取点在 `collectors/sporttery.py` 的 `save_odds_snapshots()` 内部，作用是**去重比对**（判断这次赔率跟上次一不一样），不是给模型用。
- `models/market.devig()` 只挑 `odds_json` 里当前那一个 `jc` 值去水。历史值被后续采集**覆盖**。
- 结论：**变化幅度、变化方向、变化速度，一个都没进模型。**

### 为什么应该做

盘口从初盘走向即时，反映的是资金流向与市场共识的修正。已实测到真实信号，例如 26131 期：

```
勒沃库森 vs 莱比锡红牛    1.91/3.95/2.85
                         1.87/4.00/2.90
                         1.83/4.10/2.95     ← 主胜三连降，资金持续压主队
```

### 为什么现在不做

**鸡生蛋问题**：任何改法都需要回测验证，而回测需要历史赔率变化数据 —— 而那恰恰是现在没有的（快照从 2026-09-20 才开始积累）。

这与项目一贯原则一致：**先有基线，再谈增量**。当前基线（不含变化）的真实战绩正在记录中，先跑出一批期次再说。

### 重新捡起来的条件

**至少积累到能覆盖一个完整回测窗口的期次**（建议 ≥ 50 期，或 ≥ 3 个月），且这些期次里**每一场都有完整的初盘→即时序列**。

### 候选改法（三选一或组合，都需回测）

| 方式 | 公式/做法 | 代价 |
|---|---|---|
| 漂移并入概率 | `p = devig(即时) + α × (devig(即时) − devig(初盘))` | α 需回测调参 |
| 作为 GBDT 特征 | 在 `features/build.py` 的 `FEATURE_COLUMNS` 加"赔率变化量"列 | 需改特征管线并重训 |
| 只做选场筛选 | 不碰概率，只挑"资金明显流入"的场次投注 | 改的是策略而非模型 |

### 一个必须记住的采集教训

26131 是 **9/16 20:00 开卖**的，而 watch 进程 **9/20 13:42** 才启动 —— 前 4 天的盘口演变全部错过。

所以文档里那些"初盘 1.91"其实是"我们第一次看到的价"，**不是真正的开盘价**。

**要让数据可用，watch 必须在每个期次开卖时就启动**（或做成常驻服务）。否则永远只能拿到半截序列。

### 关键入口

- 快照表：`odds_snapshots`（`period_match_id, source, captured_at, h, d, a`）
- 采集：`collect-odds --watch --interval 600`
- 消费点：`models/market.devig()`、`models/pipeline.period_predictions()`

## 2. 多公司赔率 / 亚赔 / 凯利指数（500.com 路线）【优先级：低】

### 现状

未实现。用户明确要求**推迟**，先看方案 1（官方竞彩赔率）够不够用。

### 已完成的可行性调研（结论要记住）

| 项 | 结果 |
|---|---|
| `live.500.com/?e=<日期>` 赛程页 | **可访问**（无 WAF），但页面**不含赔率**，只有跳转链接 |
| `odds.500.com/fenxi/ouzhi-{fid}.shtml` 欧赔页 | **被 WAF 拦**（987 字节挑战页） |
| WAF 第一层 | 自定义混淆 JS，可离线解出 cookie（`__tst_status`、`EO_Bot_Ssid`）。已破解 |
| WAF 第二层 | **腾讯云 EdgeOne 交互式验证码**（`TencentEOCaptchaWidget`），**必须人工点击** |
| 第二层的突破口 | `ticket_timeout = 2592000` —— **验证一次管 30 天** |
| 未验证的风险 | cookie 是否绑定设备指纹 / UA / IP。若绑了，就得常驻真实浏览器，成本翻倍 |

估算工作量：人工过一次验证码 + HTML 解析几十家公司 × 初盘/即时 × 欧赔/亚赔 ≈ **3–5 天**，且需**持续维护**（对方改版就失效）。

**风险提示**：这是明确绕过商业 WAF，可能违反服务条款。

### 什么时候值得做

先看官方竞彩赔率（已接入）的**当期预测真实命中率**。如果战绩稳定，且确认欧洲盘/亚盘能带来增量，再评估。

### 另一个更便宜的替代：补别名 + football-data

当前 `team_alias` 对当期 14 场只解析 20/28，未命中的是别名变体，例如：

```
巴伦西亚   vs 种子里的「瓦伦西亚」
巴黎圣日尔曼 vs 种子的「巴黎圣日耳曼」
莱比锡红牛  vs 种子的「莱比锡」
皇家贝蒂斯  vs 种子的「贝蒂斯」
```

补进 `collectors/team_alias.py` 的 `ALIASES` 或 `SEED` 成本极低。

**但要注意**：实测证明补别名对**映射成功率帮助有限** —— 因为失配的主因不是别名，而是 **football-data 只覆盖 9 个联赛**（E0/E1/D1/I1/SP1/F1/N1/P1/SC0），而胜负彩混编亚运会、欧冠、欧罗巴、各国杯赛、二级联赛。近 40 期实测映射率仅 **12.3%**。

所以补别名只解决"差一点点"的那部分，不要期待它解决覆盖问题。

## 3. 期次级方案回测（`backtest-plans`）【优先级：中】

### 现状

`data/reports/plan_backtest.json` 是 2026-09-18 生成的，里面**只有 26080 一期**、投入 108 元、回报 0 —— 因为当时库里就一期数据。

### 现在可以做了

库里已经有 **747 期**历史开奖（含 14 场对阵 + 赛果 + 奖金），`backtest-plans` 第一次具备统计意义：

```bash
.venv/Scripts/python.exe -m football_lottery.cli backtest-plans --years 4
```

### 但要注意一个根本限制

这些历史期次**没有当期赔率**（竞彩接口只给当天在售，无法回溯；football-data 覆盖不足）。所以期次回测只能用**当时已有的赔率**（多数为空），或退化为"比赛级口径"。

**这意味着**：真正有意义的"方案 ROI 回测"要等**当期积累够多**之后才能做 —— 这也是为什么当前策略是"从现在开始记录真实战绩"。
