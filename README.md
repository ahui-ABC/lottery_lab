# lottery-lab

竞彩 · 胜负彩 · 数字彩 的数据采集与分析工具。**重点不是「能预测」，而是「测量能不能预测」。**

采集官方开奖与赔率数据，用可复现的回测回答一个问题：这些模型和策略，到底有没有跑赢
「什么都不做」——赔率市场、以及纯随机。

## 目前的结论：都没有

这不是谦虚，是这个仓库里跑出来的真实结果。三条业务线分别验证过：

| 业务 | 对照基准 | 结论 |
|---|---|---|
| **胜负彩**（14 场） | 赔率市场（去水后） | 自研 GBDT 与融合模型**均未跑赢市场**，线上已降级为直接用市场概率 |
| **竞彩**（串关） | 随机选场 | 串关策略实测返还率 64.6%–75.3%，**长期负期望**（抽水 12%–31% 决定） |
| **数字彩**（5 类） | 随机选号 | 五条选号策略 20 组配对检验 **p 值全部 > 0.14**，与随机不可区分 |

胜负彩的具体数字（2024-08-01 起，同场对照 6,288 场）：

| 路径 | logloss | Brier | 准确率 |
|---|---:|---:|---:|
| 赔率市场 | **0.97556** | **0.58135** | **0.52704** |
| GBDT | 1.15064 | 0.67575 | 0.45197 |
| 融合候选 | 0.97760 | 0.58271 | 0.52560 |

融合模型 logloss 比市场**高** 0.002，没有增量，因此线上配置
`fusion.mode: market_primary`：保留市场概率，只在市场数据缺失时才用模型兜底。
完整记录见 [`docs/回测记录.md`](docs/回测记录.md)，数字彩部分见
[`docs/数字彩回测结论.md`](docs/数字彩回测结论.md)。

**彩票的期望值由抽水决定，不由模型决定。** 这个项目能做的，是把「有多亏」量清楚，
以及在极少数情况下（比如某个玩法的赔率定价明显偏离）识别出信号。目前没有找到。

## 功能

### 胜负彩（14 场 / 任选九）
- 当期对阵与在售期次采集
- 去水概率（Shin 三分支）、Dixon-Coles、GBDT 三种预测路径并存对照
- 约束求解器生成投注方案（预算约束下最大化期望/命中率）
- 逐期走查回测，与赔率市场同场对照

### 竞彩（5 种玩法）
- `胜平负 / 让球胜平负 / 比分 / 总进球 / 半全场` 赔率采集，**只在变化时追加快照**，记录盘口变化规律
- 历史回填（2021 年至今，约 2.5 万场）
- 五条预测路径（market / trend / stable / cross / blend）并行记录，可离线比较
- 串关方案引擎：按市场概率选场 + 同时下注所有 2 串 1 及以上组合
- 实际盈亏跟踪（不只回测，还记录真实荐单的战绩）

### 数字彩（大乐透 / 双色球 / 排列三 / 排列五 / 福彩3D）
- 2020 年至今全部开奖入库（约 9,000 期，含奖级明细）
- 五条选号策略：随机 / 热号 / 冷号 / 遗漏 / 贝叶斯
- 逐期走查回测 + 与随机选号的**同期限配对 t 检验**
- 每期推荐入库、开奖后自动对奖、累计盈亏跟踪

### Web 界面
本地仪表盘：概览、胜负彩预测与方案、历史战绩、竞彩串关方案与盈亏曲线、
数字彩各彩种详情、采集控制台（手动采集任务守护进程状态）。

## 快速开始

要求 Python 3.13+（开发环境为 3.14）。

```bash
python -m venv .venv
.venv/Scripts/activate          # Windows
pip install -r requirements.txt
pip install -e .                # 需要 setuptools

# 初始化并采集（举例）
python -m lottery_lab.cli collect-period        # 胜负彩当期对阵
python -m lottery_lab.cli collect-jc-history    # 竞彩历史回填（较慢）
python -m lottery_lab.cli collect-lottery       # 数字彩开奖

# 起服务
python -m lottery_lab.cli serve                 # 默认 http://127.0.0.1:8767
```

## 常用命令

| 命令 | 作用 |
|---|---|
| `collect-period` / `collect-draws` | 胜负彩当期对阵 / 历史开奖与赛果 |
| `collect-history` | football-data 联赛历史（增量，过去的赛季自动跳过） |
| `collect-odds [--watch]` | 竞彩赔率快照（`--watch` 为常驻轮询） |
| `collect-jc-history` | 竞彩历史回填（断点续传） |
| `predict-jc` / `plan-jc` / `score-jc` | 竞彩预测 / 串关方案 / 对奖 |
| `collect-lottery` | 数字彩开奖同步（默认增量，`--full` 补缺口） |
| `predict-lottery` / `score-lottery` | 数字彩生成推荐 / 对奖 |
| `daily-jc` / `daily-lottery` | 两条业务线的「一条龙」（预测 + 方案 + 对奖） |
| `backtest` / `backtest-lottery` | 胜负彩模型回测 / 数字彩逐期走查 |
| `serve` | 启动本地 Web 仪表盘 |

数据落在 SQLite（默认 `data/football.db`，见 `config.yaml`）。

## 数据来源

全部使用**官方接口**，不需要认证：

| 数据 | 来源 |
|---|---|
| 胜负彩 / 竞彩 | `webapi.sporttery.cn`（中国体彩官方网关） |
| 联赛历史与赔率 | [football-data.co.uk](https://www.football-data.co.uk/) CSV |
| 数字彩（大乐透 / 排列三 / 排列五） | `webapi.sporttery.cn` |
| 数字彩（双色球 / 福彩3D） | `www.cwl.gov.cn`（中国福彩官网） |

早期版本曾抓第三方数据站，每期一个请求。实测**6 并发无间隔约 1000 次请求后整个 IP 被
WAF 封禁**，随后改为官方接口：100 期/请求，6 年数据从约 8000 个请求降到约 85 个。

采集侧的护栏：全局限速令牌桶、撞 403/429 立即中止而非硬撞、手动采集任务**同一时刻只允许跑一个**。
被限流时只降速，不换 UA、不换代理。

## 若干工程笔记

采集与回测过程中踩到、并且修掉的坑，都写进了代码注释和设计文档。几个有代表性的：

- **`upsert` 会静默覆盖快照。** 赔率快照是「某时刻的观测值」，必须追加；用了
  `ON CONFLICT DO UPDATE` 会导致历史赔率被新值盖掉，变化规律无从谈起。开奖数据则相反 ——
  那是既成事实，覆盖才对。
- **体彩接口用 `-1` 表示「该项不适用」。** 按「去掉非数字字符」解析会把它变成正的 `1`，
  静默把哨兵值当成奖金。
- **同一字段名在两个数据源里语义不同。** 福彩 `prizegrades.typemoney` 在双色球是**单注**奖金，
  在 3D 是**总**奖金。混用会把 3D 直选的 1759 万当成单注金额。
- **奖级规则会变。** 大乐透 2026-02-02 起由 9 个奖级改为 7 个，三等奖从「5+0」并入
  「5+0；4+2」。回测按当期奖级表里有没有「九等奖」判断适用哪套规则，不按日期硬编码。
- **`pythonw.exe` 是 launcher。** venv 的 `pythonw.exe` 会派生真正的解释器作为子进程，
  只 kill `Popen.pid` 会留下孤儿进程；必须 `taskkill /F /T`。
- **重定向到文件时 Python 默认块缓冲。** 后台任务的实时日志需要 `-u`。

## 已知限制

- **不做历史预测回填。** 预测必须在开奖/开赛前产生，事后补算等于偷看答案。
  因此盈亏统计只覆盖系统上线后真实产生的荐单，初期样本很小。
- **数字彩的可预测性**：摇奖机独立同分布，历史号码对下一期没有信息量。这个子项目提供的是
  「一个能被证伪的预测 + 证伪它的回测」。
- **竞彩赔率变化尚未参与计算。** 变化快照从 2026-09 才开始积累，回测需要历史变化数据，
  暂时无法验证其增量价值。见 [`docs/后续工作.md`](docs/后续工作.md)。
